Core rule

Any number of readers may access the database together, but a writer requires exclusive access. Readers and writers must never access the shared database at the same time.

mutex = 1

mutex protects only the shared reader counter rc. It prevents two readers from changing the counter simultaneously.

db = 1

db controls access to the database. A writer acquires it alone. Readers acquire it collectively through the first reader.

rc = 0

rc records how many readers are currently inside the reading section. It must only change while mutex is held.

First-reader and last-reader pattern

The first reader changes rc from 0 to 1 and performs down(db), closing the database to writers. Later readers only increment rc and may read concurrently. The last reader changes rc from 1 to 0 and performs up(db), allowing a waiting writer to continue.

From a writer's perspective: db behaves like a regular mutex. From the readers' perspective, the entire reader group collectively holds it.

Reader-preference solution

Reader

while (true) {
    down(&mutex);
    rc++;
    if (rc == 1) down(&db);
    up(&mutex);

    read_db();

    down(&mutex);
    rc--;
    if (rc == 0) up(&db);
    up(&mutex);
    use_data_read();
}

Writer

while (true) {
    think_up_data();
    down(&db);
    write_db();
    up(&db);
}

Why writer starvation is possible

While a writer waits on db, new readers may still enter as long as at least one reader remains active. If readers continue arriving before rc reaches zero, the reader group never releases db. The writer can therefore wait indefinitely.

This is a reader-preference algorithm. A fair or writer-preference solution requires an additional turnstile, queue, or semaphore that prevents newly arriving readers from passing a waiting writer.

Important detail

The first reader may block on down(db) while still holding mutex. This prevents other readers from modifying rc until the first reader has successfully established the reader group's access to the database.
