What a monitor provides

A monitor bundles shared state, procedures that operate on it, and synchronization rules into one module. At most one thread executes a monitor procedure at a time, so calls to enter and remove are automatically serialized.

The caller does not explicitly lock and unlock the buffer. Entering a monitor procedure acquires its implicit lock; returning releases it.

Implicit monitor lock

Protects count and the buffer from simultaneous modification.

full condition

Holds producers that cannot proceed because the buffer has no free slot.

empty condition

Holds consumers that cannot proceed because the buffer has no item.

The essential behavior of wait

  1. The caller joins the chosen condition-variable queue.
  2. It atomically releases the monitor lock and suspends.
  3. Another thread may now enter the monitor and change the state.
  4. After being signaled, the caller must reacquire the monitor before continuing.

If wait kept the monitor locked, the program would deadlock: no producer or consumer could enter to make the awaited condition true.

Safer bounded-buffer pseudocode

Monitor procedures

monitor ProdCons {
  condition full, empty;
  int count = 0;

  void enter(item) {
    while (count == N)
      wait(full);
    insert_item(item);
    count++;
    signal(empty);
  }

  void remove(item*) {
    while (count == 0)
      wait(empty);
    *item = remove_item();
    count--;
    signal(full);
  }
}

Client code

void producer() {
  while (true) {
    item = produce_item();
    ProdCons.enter(item);
  }
}

void consumer() {
  while (true) {
    ProdCons.remove(&item);
    consume_item(item);
  }
}

Producing and consuming happen outside the monitor, keeping the protected region short.

Why use while instead of if?

Many real systems, including Java-style monitors, use Mesa semantics: signal/notify makes a waiter eligible to run but does not transfer the monitor immediately. By the time that thread reacquires the monitor, another thread may have changed the state. Rechecking the predicate in a while loop is therefore the robust pattern and also handles spurious wakeups.

signal is not stored

A condition variable is a waiting queue, not a counter. If nobody is waiting, signal has no remembered effect. This is not a lost wakeup when the condition is always checked while holding the same monitor lock: a thread either observes that it can proceed, or it atomically releases the lock and joins the wait queue.

Monitor semantics vary

  • Hoare semantics: the awakened thread runs in the monitor immediately; the signaling thread yields it.
  • Mesa semantics: the awakened thread becomes runnable and later competes to reacquire the monitor. Most common programming environments follow this style.
  • Java: synchronized supplies the monitor lock; wait() releases it; notify() wakes one waiter; notifyAll() wakes all waiters.
