What a semaphore does

A semaphore stores an integer value and supports two atomic operations. down(), also called wait() or P(), decreases the value when a resource is available; otherwise, it blocks the caller. up(), also called signal() or V(), releases a resource and wakes a blocked process when needed.

Why no lost wakeup? An up() operation is remembered in the semaphore value even when nobody is currently blocked. A later down() consumes that stored signal.

empty = N

Counts unused buffer slots. The producer performs down(empty) before insertion. When the buffer is full, empty = 0 and the producer blocks.

full = 0

Counts available items. The consumer performs down(full) before removal. When the buffer is empty, full = 0 and the consumer blocks.

mutex = 1

Serializes access to the shared buffer. A process performs down(mutex) before changing the buffer and up(mutex) afterward.

Relationship among the counts

empty + full = N

This equality holds when no producer or consumer has reserved a slot or item between semaphore operations. During an insertion or removal, the sum may temporarily be less than N because a resource has been reserved but the matching up() has not occurred yet. The animation uses five slots; the original example uses N = 100.

Semaphore solution

Producer

while (true) {
    item = produce_item();
    down(&empty);
    down(&mutex);
    insert_item(item);
    up(&mutex);
    up(&full);
}

Consumer

while (true) {
    down(&full);
    down(&mutex);
    item = remove_item();
    up(&mutex);
    up(&empty);
    consume_item(item);
}

Why three semaphores?

empty and full answer resource questions: “Is there a free slot?” and “Is there an item?” mutex answers a different question: “Who may modify the shared buffer now?” Combining these responsibilities makes the code harder to reason about and can introduce races or deadlock.

Can two be enough? Specialized single-producer/single-consumer ring buffers can sometimes avoid a mutex through carefully designed atomic indices. For this general shared-buffer solution, especially with multiple producers or consumers, all three synchronization roles are needed.

Why operation order matters

A producer checks empty before acquiring mutex; a consumer checks full before acquiring mutex. If a process locked mutex first and then blocked on an unavailable resource, it could prevent the other process from entering the buffer to create that resource, causing deadlock.

Discussion questions

  • What changes when the producer executes down(empty)?
  • Why does the consumer signal empty after removing an item?
  • Why can only one process hold mutex at a time?
  • What deadlock could occur if down(mutex) came before down(empty) or down(full)?
