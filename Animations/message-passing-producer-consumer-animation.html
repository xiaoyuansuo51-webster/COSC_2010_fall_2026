Message Passing: Producer–Consumer

Follow a fixed set of message buffers as they circulate between a producer and consumer. Empty messages represent permission to produce; full messages carry completed items.

The central idea

The system owns exactly N reusable message buffers. Initially, the consumer sends all N empty messages to the producer. To create an item, the producer must first receive one empty message, fill it, and send it to the consumer. After consuming the item, the consumer sends that same message back empty.

The empty-message pool is also the capacity control. If the producer has no empty message to receive, all N buffers are full or in use, so the producer blocks automatically.

Synchronization

Blocking receive suspends a process when its mailbox contains no suitable message.

Communication

A full message moves the item from the producer’s address space to the consumer.

Bounded capacity

Only N messages circulate, so at most N produced items can await consumption.

Pseudocode from the example

Producer

while (true) {
  item = produce_item();
  receive(consumer, &msg); // get empty
  build_message(&msg, item);
  send(consumer, &msg);    // send full
}

Consumer

for (i = 0; i < N; i++)
  send(producer, &msg);    // seed empties

while (true) {
  receive(producer, &msg); // get full
  item = extract_item(&msg);
  send(producer, &msg);    // return empty
  consume_item(item);
}

Why the names can look backward

In this textbook notation, send(destination, message) names the destination, while receive(source, message) names the expected source. Therefore, the producer’s receive(consumer, &msg) receives an empty message previously sent by the consumer. The consumer’s receive(producer, &msg) receives a full message sent by the producer.

A blocked process becomes runnable when the required message arrives.

Important assumptions

  • send and receive are operating-system primitives with well-defined atomic queue operations.
  • Messages are not silently duplicated or lost by the abstraction.
  • The example uses blocking receive. Nonblocking receive would need explicit handling for “no message available.”
  • Messages sent by the producer are delivered to the consumer’s mailbox and vice versa.
  • Initialization must create exactly N distinct empty message buffers—not repeatedly enqueue an unsafe reference to one mutable object.

Message passing versus shared memory

Mutexes, semaphores, and monitors coordinate access to shared state. Message passing instead exchanges data explicitly and can work even when processes do not share memory, including across machines. The operating system or runtime still needs internal synchronization to manage mailboxes safely.

Common design choices

  • Direct communication: processes name each other, as in this example.
  • Indirect communication: processes send to named mailboxes, ports, or channels.
  • Zero capacity: sender and receiver rendezvous; neither message can wait in a queue.
  • Bounded capacity: at most a fixed number of messages wait.
  • Unbounded capacity: sends normally do not block for lack of queue space, although real resources remain finite.

Discussion questions

  • Why are N empty messages sent before production begins?
  • How does the empty-message pool replace an explicit “empty slots” semaphore?
  • What blocks the consumer when there is no item?
  • What changes if send is synchronous rather than buffered?
  • Why must the initialization create N independent message buffers?
